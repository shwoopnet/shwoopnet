# SCAN HARNESS: one shared, vectorised rule scanner (owner mandate Nov 7, 2026)

Research only. `src/scalper/scan.py` (library plus CLI), tests `tests/test_scan.py`, ledger `workers/scan_ledger/`. No trading code, no key, no network, no order.
Everything below is what the code does today; if the two ever disagree, the code and its tests win and this file is wrong.

## Use
```
python3 -I src/scalper/scan.py selftest              # registered README figure + engine vs plain loop (0.6 s)
python3 -I src/scalper/scan.py bench                 # rules per second on a synthetic table (no real rule scored)
python3 -I src/scalper/scan.py ledger                # N and the Bonferroni bar, read back from disk
python3 -I src/scalper/scan.py unseen --adapter all  # how much data each adapter leaves unread (counts only)
python3 -I src/scalper/scan.py run --adapter kalshi_fresh --n 5000 [--seed K]     # one RUN, writes data/scan/runs/*.json
python3 -I src/scalper/scan.py freeze --run data/scan/runs/<file>.json --id <ID>  # workers/SCAN_FROZEN_<ID>.json + .sha256
python3 -I src/scalper/scan.py audit --frozen workers/SCAN_FROZEN_<ID>.json       # 7 audit hooks, development data only; writes workers/SCAN_AUDIT_<ID>.json + .txt
python3 -I src/scalper/scan.py holdout --frozen workers/SCAN_FROZEN_<ID>.json     # the ONE holdout read
```
Perps adapters: `--adapter perps_crypto|perps_noncrypto`, optional `--perp-frozen-id <existing PERPGEN id>` to include the validation third. From Python: `from scalper import scan` then `ad = scan.KalshiAdapter(scan.FRESH); tab = ad.build_dev(); scan.run(ad, 5000, seed, tab=tab)`.
A worker's own idea is a new `Adapter` subclass (build_dev, build_holdout, unseen, truncation_test) returning a `Table`; the grammar, ledger, bar, guard and audit then come for free. Every `run` appends to the ledger BEFORE scoring, so a scan is a try whether or not anyone reads its output. Run `selftest` first; it writes nothing and counts nothing.

## The bar (owner's, unchanged; printed at the top of every scan)
A survivor needs profit factor 1.5 or better in EACH of W1, W2, W3 after fees. 1.5 is never raised for N. Floors (separate from the PF bar, `scan.BAR`): 40 trades per window, 150 trades total (the README floor), 3 distinct dates per window. A survivor is labelled `deflated` when its day-clustered z over all development cells is at least the one-sided Bonferroni z at 0.05 / N. A survivor must then hold up ONCE on the held-out last third: PF 1.5 or better, at least 50 trades on at least 5 dates (`HOLD_BAR`). Labels at the holdout: FALSIFIED (PF under 1.5), NOT_ENOUGH_DATA (floors not met), LEAD (holds but not deflated in development), CANDIDATE (holds and deflated). A CANDIDATE permits a forward paper test only, as in PERPGEN; nothing here permits anything live, and a named counterparty is still required by the registration of whoever runs it.

## The fee (exact)
`kalshi_fee_cents(p, c, mult) = ceil(mult x 0.07 x c x p x (1 - p) x 100 - 1e-9)` cents per ORDER of c contracts at price p in dollars (taker at the ask, as in the README FEE1 note and the live bot); per contract it is that over c. The 1e-9 is the guard gen1.py, gen2.py and l1studies.py already use (an exact whole-cent product is not rounded up on float noise). Net of a hold-to-settlement buy: `(payoff - ask) x 100 - fee / c` cents per contract, payoff 1 or 0, no exit fee. Default c = 1 (`KalshiSpec.contracts`); 10 contracts at 50c is 18c for the order, 1.8c each. The stress column uses mult 1.2 (the README's "fees x1.2"). A NO buy is priced at `round(1 - YES bid, 4)`.
Perps: 12 bps of notional per side (PERPGEN's placeholder, not confirmed against Kalshi's fee page), stress 24 bps per side, funding with the ASSUMED sign (long pays a positive rate); the recorded bid and ask crossing is in the prices.

## Windows and cuts
- Development region of each adapter is cut into W1, W2, W3 by thirds of its distinct UTC dates (Kalshi: close date, pooled over series; perps: per ticker over its own dev days, like PERPGEN). Window cells are (window, date), and "day-clustered z" is the mean of per-cell mean nets over (their sd over sqrt(cells)).
- Atoms: numeric feature, `ge` or `le`, quantile in {0.10, 0.25, 0.50, 0.75, 0.90}, the cut value being that quantile of the feature over W1 rows only (per ticker for perps), computed once (sha256 of the cut table is stored in every run and frozen file) and never re-estimated, not for W2, W3 or the holdout. Categorical atoms: feature equals a value. A missing feature value makes its atoms false. 1, 2 or 3 atoms on distinct features (probabilities 0.2, 0.4, 0.4), direction, look time (Kalshi, seconds before the close, 840 to 180 step 60) or hold (perps, 15 min to 24 h).
- Kalshi features (all from candles ending at or before the decision, `kalshi_row`): ask, bid, spread, d1 d2 d3 d5 (change of the side's bid over 1, 2, 3, 5 minutes), rng5, vol, doi (change of open interest over 3 minutes), nprev, hour; categorical series, hod4, dow. Perps (`perp_features`): r5..r1440, vol60, vol240, rng60, rng240, sp, spr, vlr15, vlr60, doi60, doi240, dhi/dlo 240 and 1440, pir1440, tvm, fr_last, fr_chg, fr_avg3; categorical hod4, dow, wkend. Cross-asset leads and minutes-to-funding are v1.1 and opt-in (see "v1.1 perps features" below); without the flag they are not there.

## How N is counted
One ledger line = one distinct (dataset, group, rule) scored: `dataset|group|atoms (sorted)|direction|look-or-hold`, e.g. `kalshi15_fresh|ALL|ask:ge:0.75&hour:le:0.50|yes|360`. A RUN draws distinct rules with `random.Random(seed)`, skips any id already in any scan ledger, and appends the batch (2,000 rules) to `workers/scan_ledger/<dataset>_<group>_RUN<seed>.ids.gz` and closes the file BEFORE scoring it (a test crashes the scorer and finds the batch counted). **N = `scan.prior_n()` + lines of `workers/perpgen_ledger/*.ids.gz` + lines of `workers/scan_ledger/*.ids.gz`**, all read back from disk by `scan.n_total()`; `workers/scan_ledger/PRIOR_N.json` holds the lead's tally before the PERPGEN ledgers (730,489 at registration). Today: 730,489 + 500,000 + 0 = 1,230,489, one-sided Bonferroni z = inverse normal of 1 - 0.05 / N = **5.364**. The bar is recomputed at the end of every run from the ledger as it then stands. Edit `prior_n` only when the lead publishes a new tally of non-ledgered tries; never lower it. Tries made outside the harness (a hand-written rule) still need adding to `prior_n` by the lead.

## Speed, and what the screen ignores
The screen builds a (B x rows) boolean mask per batch with `A[a0] & A[a1] & A[a2]` over a precomputed atom matrix, then ONE float32 matrix product with a (rows x 12) window matrix gives trades, gross wins, gross losses and winners for every rule in every window. Days per window, day-clustered z, the perps overlap rule (one position per ticker) and float64 sums are applied only to rules that pass the screen (`exact_rule`, plain float64). The screen is slightly loose (`SCREEN_SLACK`) so float32 rounding cannot drop a rule; a rule that fails the screen only because overlapping perp signals inflated its trade count is a possible miss, and is still counted in N.

## What each adapter leaves unseen (`scan.py unseen`; counts only, nothing opened)
- `kalshi_fresh` (`data/fresh.sqlite`, 18 series): development = closes before 2026-10-28 (2026-10-11 to 10-27, 17 dates, 22,950 settled windows, 513,359 decision rows over 12 looks and two sides, W1/W2/W3 = 6/6/5 dates). **Unseen: the 12,569 settled windows closing 2026-10-28 to 11-05 (about 301,656 decision rows), behind the guard.** This is GEN1's and OICOREX1's cut (F2): do not unlock before 2026-11-08 and coordinate with them, and F11 (windows after 10-30) is also read by the GEN5 candidate file. The development region lies inside the README ledger's W3 (F1); it is dev here only because F2 puts the registered holdout line at 10-28, and GEN1 and GEN2 already read it, so it is NOT fresh data for them. Rows from 10-28 on are never selected by the dev SQL (the cut is a bind parameter and the loader refuses a read that crosses it).
- `perps_crypto` (10 tickers) and `perps_noncrypto` (6): without a frozen id only each ticker's DISCOVERY third is loaded (`perpdata.load_stage`). Unseen: validation (locked by perpdata until a `PERPGEN_FROZEN_<id>.json` exists, and already read by earlier PERPGEN runs) and the holdout third, 506 ticker-days (about 48,576 quarter-hour decisions) for crypto and 76 ticker-days (about 7,296) for noncrypto, from `PERPGEN_CUTS.json`; the 28-ticker holdout is 1,244,096 one-minute rows (DATA_INVENTORY G02, counted there by lines). The perps holdout needs BOTH `perpdata.load_holdout`'s own guard and this harness's.

## Holdout guard (read once)
`data/scan/holdout_guard.json`, git-ignored, written BY HAND after the frozen list is committed and pushed: `{"unlock": {"<frozen id>": {"datasets": ["kalshi15_fresh"]}}}`. `holdout` then (1) checks `workers/SCAN_FROZEN_<id>.json` against its `.sha256` sidecar and that git has it committed unchanged, (2) checks the guard names that id and dataset and has no use record, (3) writes the use record BEFORE it builds the holdout rows (a crash cannot allow a second read), (4) scores the frozen rules with the frozen cut points and writes `workers/SCAN_HOLDOUT_<id>_RESULT.json`. A failed read is final; a frozen id is never reused (`freeze` refuses it). Dev loaders cannot return a holdout row.

## Audit hooks (`scan.AUDIT_HOOKS`, `scan.run_audit`, `scan.audit_frozen`, dev data only; HARNESS v1.1, Nov 7, 2026)
`python3 -I src/scalper/scan.py audit --frozen workers/SCAN_FROZEN_<ID>.json [--perms 1000] [--perp-extra]` builds the adapter's DEVELOPMENT table (never a holdout row), rebuilds the atoms from the frozen cuts, runs every hook on every survivor, prints a short summary, writes `workers/SCAN_AUDIT_<ID>.json` and `.txt`, and exits 2 if any hook fails or the cuts sha differs from the frozen one. Library: `scan.audit_frozen(adapter, doc, tab=None, out_dir=None, perms=None)`; each hook also exists as a function (`placebo_shuffle`, `plain_recompute`, `latency_stress`, `cluster_dedupe`). Register more with `@scan.audit_hook`.
1. `audit_truncation`: for 200 random rows, delete every candle or bar after the decision time (and, with the perps extras, every leader minute and funding row after it) and recompute the features; they must equal the stored ones. A deliberately leaky synthetic feature fails 100 of 100.
2. `audit_reverse_control`: the same entries in the opposite direction must have PF under 1.0 (perps only; not defined for Kalshi).
3. `audit_fee_stress`: pooled PF at the stress cost (fees x1.2; perps 24 bps a side) at least 1.0.
4. `audit_placebo` (`placebo_shuffle`): keep the rule's selection, shuffle the outcome (net per row of the rows that direction and look or hold can trade) within blocks of (ticker, UTC date), rescore, 1,000 permutations, seed 20261107. Reports the share of permutations whose pooled PF reaches the observed one (`share`), the same for the weakest window (`share_min_window`) and `p_plus = (1 + hits) / (1 + perms)`. Passes at p_plus under 0.05 for every survivor. CAVEAT: it is per rule and NOT corrected for the many rules the survivor was picked from (the best of 300 noise rules has an unremarkable p, tested); the deflation is the z bar, not this. It catches a selection that adds nothing over a random pick of the same days' outcomes (a day or cost artefact).
5. `audit_plain_loop` (`plain_recompute`): a second implementation written from the fee function and the settlement definition: python floats, `math.ceil`, one trade at a time, its own thirds of dates, its own atom evaluation (float32 compare against the frozen cuts), its own perps fills (entry bar, first usable exit bar within 5 minutes, funding in (entry, exit], spread defect rule, one position per ticker). It must give the same set of trades and the same n, days and PF (relative 1e-4) in each window as `exact_rule`; any difference raises `AuditMismatch` (library, strict) or fails the hook (CLI exit 2). It shares only the feature definitions (`kalshi_row`, the perps feature arrays; Kalshi features are recomputed from the candles, perps features are read from the table), which hook 1 audits. **It found a real defect on its first run:** the perps `exit_ts` array was float32, and a unix time in float32 rounds by up to 64 seconds, so the one-position-per-ticker rule dropped or kept the wrong signals (106 and 160 trades of about 1,200 differed on a BTC and ETH long rule). Fixed (float64); no scan or PERPGEN result used it (the scan ledger had 0 lines).
6. `audit_latency` (`latency_stress`): the rule is still decided at its own row and filled later. Kalshi: the look moves from L to L-60 and L-120 seconds (6 minutes left becomes 5 and 4), the entry ask is that later quote, no usable quote there is a MISSED fill (counted, not traded). Perps: entry and exit one and two minute bars later, the one-position rule on the later exits. Reports PF and n per window, pooled PF and missed fills; passes at pooled PF >= 1.0 at both shifts (the 1.5 bar is not re-applied).
7. `audit_cluster` (`cluster_dedupe`, informational, no pass or fail): the Jaccard overlap of the set of traded window ids (Kalshi: the market; perps: ticker and decision time), threshold 0.7. Greedy: survivors are taken by weakest-window PF, best first; one joins the first representative with Jaccard over 0.7, else starts a cluster. Clusters are not transitive, so the count K of independent survivors is conservative. Quote K, never N survivors.

## v1.1 perps features (opt-in: `PerpAdapter(extra=True)`, CLI `--perp-extra`; a frozen file remembers it in `adapter_opts`)
With the flag off the atoms, rule ids and ledger lines are exactly v1's. With it on, the table gains `FEATS_PX` = xbtc15, xbtc60, xbtc240, xeth60, xeth240, rel_btc60, rel_btc240 (leader log mid return over the window ending at the decision minute, bps; rel = own r60 or r240 minus BTC's) and the categorical `mtf` (minutes to the next funding: 0 under 30, 1 for 30 to 120, 2 for 120 to 240, 3 for 240 and over, -1 missing). A leader's value is used only where the leader's own loaded region (the same stage this adapter reads for it: discovery, plus validation with a frozen id) has both end minutes; otherwise NaN and the atom is false; at a holdout read only leaders that are themselves in the guarded read count (a leader outside the table is never opened). BTC does not lead BTC and ETH does not lead ETH. `mtf` takes the calendar from funding rows published at or before the decision (the distinct seconds of day of the last 6 settlements, so the clock change moves it one settlement late rather than looking ahead), which matches the registered 04, 12, 20 UTC crypto calendar (05, 13, 21 after the change) and the daily calendars of the rest. NOT built: xgold60 and xus500_60 of the protocol (BTC and ETH only here), volratio.

## Still missing (nothing here assumes them)
Concentration checks (one day or one series carrying the PF); a selection-corrected placebo (the best-of-N null, which would need the whole scan repeated on shuffled outcomes); latency on the exit side for Kalshi (positions are held to settlement, so only the entry matters there); a plain-loop recompute of the perps FEATURES (hook 5 reads them from the table; hook 1 and the feature tests guard them); xgold60 and xus500_60; Kalshi order-size and queue effects (taker at the ask, one contract, no depth); the PERPGEN `A4` funding-timing test (delay the rate by an interval) is not a hook here; holdout-time audits (by design: the audit never reads a holdout).
