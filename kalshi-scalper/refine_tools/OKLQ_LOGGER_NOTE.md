# OKX liquidation logger (backlog row 55), DRAFT, NOT ACTIVE (Nov 10, 2026)
Files: `scripts/record_oklq.py`, `.github/workflows/record-oklq.yml`, `test/oklqRecorderGates.test.js` (OL1 to OL7, all pass). They live on `claude/refine-live` only. GitHub runs schedules only from the default branch, so nothing runs until the owner merges it after a security review. Modeled on record_rain (same pattern: public data, no key, no secret, no order, no auth header, built-in token, `quote-data` branch under `oklq/`, never main, a concurrency group that never cancels, built-in stop date, 429 backoff, always exits 0).

## What it logs
OKX `public/liquidation-orders` (keyless, GET) for `uly=BTC-USDT` (BTC-USDT-SWAP) and `uly=BTC-USD` (BTC-USD-SWAP), state=filled: `ts_ms, side, pos_side, sz, bk_px, bk_loss, ccy, inst_id, uly` plus `t_recv_ms`. `coverage.csv` has one row per underlying per pass: requests, pages, rows read, new, duplicate, oldest and newest ts, why paging stopped (`reached_seen_or_horizon`, `history_end`, `page_limit`, `read_failed`, `out_of_time`), 429 and 5xx counts, and a "possible hole" note. De-duplication: the key is instId, ts, side, posSide, bkPx, sz (OKX has no row id). The workflow checks out the data branch and passes `--seen data/oklq`, so a pass skips rows pushed earlier in the last 3 days. Analysis should still drop exact repeats.
Measured today (sandbox reached www.okx.com, HTTP 200): BTC-USDT runs about 200 rows an hour (12 pages = 1,200 rows reached back only about 6 h); BTC-USD about 70 rows in 17 h.

## Cadence and the longest safe gap
Two cron sets, `7 */2` and `37 1-23/2`: 24 triggers a day, a start every hour on average, each set every 2 h. A pass reads back from the newest row it has (minus 5 min overlap) up to a 16 h horizon (OKX keeps about 17 h; the 17 h edge is empty) and at most 40 pages per underlying (about 32 pages are needed for 16 h of BTC-USDT). **Longest safe gap between two passes that actually land: 12 hours** (16 h reach, minus a 4 h margin for busy markets and the uncertain retention edge). Over 16 h a hole appears and the coverage row says so. Scheduled starts have been dropped for days at a time on the rain recorder (RECPATCH1), so the first week should be checked on the largest gap between `t_start_ms` values in coverage.csv.

## Cost
- Requests per pass: steady state 2 to 6 (one page per underlying per hour of backlog, about 2 pages per hour for USDT), about 7 on a 2 h gap; the first pass about 13 to 35. Per day about 24 passes x about 5 = 120 to 170 requests. Rate: one stream, at least 1.0 s apart, so at most 60 a minute (OKX allows 20 per 2 s); the daily average is about 0.002 a second.
- Measured job: the script took 17.4 s for 13 requests with no seen rows (first pass); a caught-up pass took 2.0 s for 2 requests. A full job adds checkout, data branch fetch and push, about 25 to 45 s, so a run is under a minute, billed as 1 minute.
- Runner minutes: 24 runs a day x 1 billed minute x 30 days = about 720 minutes a month, so **over 250**. The repo is public, so standard Actions minutes are free; the figure is stated anyway. To get under 250, use one set only every 6 hours (4 runs a day, 120 min a month); that is still inside the 12 h safe gap but a dropped start then costs 6 h.
- Data: about 3,000 rows a day, about 40 KB gzipped a day, about 2 MB over 8 weeks.
